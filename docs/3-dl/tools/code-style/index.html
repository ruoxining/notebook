    Pythons' Code Style Guide

    :material-circle-edit-outline: 约 568 个字 :fontawesome-solid-code: 81 行代码 :material-clock-time-two-outline: 预计阅读时间 3 分钟

    PR

    First prototypes, and implementations then

    Every PR should be meaningful (an integral element)

    Split to the smallest elements

    ✅ each PR can be described within one sentence.

    git add , instead of git add .

    require review before each merging, by setting up ‘protecting your branch’

    PRs title - same as git commit message

    format [label] name + summary of change

    admitted labels: Git Commit Style Guide

    PR message - same as git commit message

    File management

    oop

    Encompass each function (except main) into a related class.

    write prototypes first

    avoid using hyphen or underscore in file naming, make files into folders instead.

    ✅ Do models/models.py

    ❌ Don't models_main.py

    Naming

    avoid abbreviations and use full spellings

    ✅ Do path_checkpoint.

    ❌ Don't path_ckpt.

    (my own habit:)

    • class name: noun-adj
    • function name: verb-noun
    • functions/files with similar functions or operate on the same objects should begin with the same substring

    Class's private members should start with an underscore _ to separate with the input parameters.

    e.g., the correct private number name should be

    def __init__(self, foo):
    self._foo = foo     # not recommended

    instead of 

    def __init__(self, foo):
    self.foo = foo      # recommended

    And whenever an outer function requires a private member of a class, it is not recommended to directly use the private member from the class like

    class Foo:
    def __init__(self, bar):
        self._bar = bar

foo = Foo()
foo._bar                # not recommnded

    nor

    class Foo:
    def __init__(self, bar):
        self._bar = bar

    @property
    def get_bar(self):
        return self._bar

foo = Foo()
foo.get_bar()

    instead, using a @property decorator is recommonded.

    class Foo:
    def __init__(self, bar):
        self._bar = bar

    @property
    def bar(self):
        return self._bar

foo = Foo()
foo.bar

    Spacing

    From top to down - In every comment: 1 space-line between each section, i.e., - Except the file top, no more than 2 space-line

    Type Hints

    write type hints, no need to write types in the comment

    ✅ Do

    def foo(bar: int) -> str:
    """
    Args:
        bar: 
    Returns:
        str: 
    """
    pass

    ❌ Don't

    def foo(bar: int) -> str:
    """
    Args:
        bar (int): 
    Returns:
        str (str): 
    """
    pass

    try to use the typing library.

    Usual usage: when you want to indicat the element type of a Dict / a List / etc.

    from typing import Dict

typing.Dict[str, Union[int, float]]

    Supported types: - Dict[x, y] - Union[x, y, ...] -

    After Python 3.10, this feature is included as an internal feature, with all types written as lower cases.

    dict[str, int | float]

    But to preserve the extenability to lower versions, I believe the importing method would be better.

    Comments

    Where should comments appear?

    • file docstring
    • class docstring
    • function docstring
    • other

    Formats

    • Required: file docstring (on the top of the file), class docstring (after the class's name), function docstring (after the function's name).

    • Either a sentence or several paragraphs.

      """A sentence describing the file content."""

      or 

      """A sentence describing the file content.

Declarations.
"""

    • Function docstring's format

      """A sentence describing the function's content.

Args:
    arg1    : explain

Returns:
    return1 : explain
"""

    file docstring

    No space between the docstring and the imports.

    Be sure to make every doc a sentence

    ✅ Do # a comment.

    ❌ Don't # a comment..

    Can omit 'the' but keep congruent

    ✅ Do 

    # comment 1.
# comment 2.
# comment 3.

    ❌ Don't

    # comment 1.
# the comment 2.
# comment 3.

    Imports

    Order

    1. import all Python default libs, in alphabetical order (of the package name instead of the folder name), and add an empty line.
    2. import all 3rd party libs in alphabetical order, and add an empty line.
    3. import all libs defined in this project.

    One way to automatically sort the imports in VSCode (Don't sing an alphabet song every time you add an import): 1. Open the setting.json. 2. Add or change the following setting

    ```json
"editor.codeActionsOnSave": {
    "source.organizeImports": true,
},
```

    Importing Names

    ✅ Do use import x, x.y to avoid the conflict of namespace, e.g.,

    import torch
import transformers

torch.nn.Module
transformers.Trainer

    ❌ Don't use from x import y.

    The only examptions are those well-established ones, e.g., from typing import Dict, List, Optional, Sequence, Union.
